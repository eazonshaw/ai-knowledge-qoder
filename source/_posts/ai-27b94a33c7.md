## 正文

Netflix has developed [Quasar, an internal tool](https://netflixtechblog.com/beyond-api-compatibility-building-a-tool-to-measure-the-blast-radius-of-library-changes-9474f2fd4f90) that identifies which repositories use specific library API symbols, helping engineering teams assess the downstream impact of proposed changes before releasing them. The tool combines semantic code indexing with API comparisons to identify affected consumers, dependency versions, and relevant call sites across repositories.

The challenge extends beyond identifying whether an API change is incompatible. Compatibility tools can flag a removed method or changed signature, but they do not necessarily identify which applications call it. Dependency graphs show declared relationships rather than actual usage, while text searches can miss references involving inheritance, overloads, and generated code. Building every downstream consumer to validate a change can also be expensive.

*Quasar architecture diagram showing the indexing and query workflow (Source: [Netflix Blog Post](https://netflixtechblog.com/beyond-api-compatibility-building-a-tool-to-measure-the-blast-radius-of-library-changes-9474f2fd4f90))*

Quasar indexes symbol definitions and references using the [SCIP Code Intelligence Protocol](https://scip-code.org/), an open format for representing code relationships. Language-specific indexers submit data during CI builds, which Quasar stores in Amazon S3 as Parquet files and queries through Amazon Athena.

During pull request analysis, Quasar compares API definitions between commits and identifies added, removed, or modified symbols. It then queries indexed references to locate affected repositories, dependency versions, and source locations. A Netflix example shows a deprecated method removal affecting 137 repositories across three library versions.

*Example Quasar impact report showing affected repositories and dependency versions (Source: [Netflix Blog Post](https://netflixtechblog.com/beyond-api-compatibility-building-a-tool-to-measure-the-blast-radius-of-library-changes-9474f2fd4f90))*

However, an absence of indexed references does not prove that an API is unused. Reflection, dynamic loading, stale indexes, and incomplete coverage can prevent Quasar from observing every consumer.

[Antonio J. del Águila](https://www.linkedin.com/in/ajdelaguila/), founder of Knaisoma, [highlighted](https://lnkd.in/p/gCTgc6vx) another limitation in a LinkedIn discussion about the approach:

> Observed usage has a blind spot for reflection and for code on rare paths, like a quarterly batch job, since those calls may never show up in the window that was sampled.

[Roberto Pérez Alcolea](https://www.linkedin.com/in/robertoperezalcolea/), a member of Netflix's Java Platform Team and author of the original article, [acknowledged](https://lnkd.in/p/gYZ9BFwh) the limitation and described ongoing work to complement static evidence:

> Reflection and incomplete indexing remain blind spots, and we’re also investing in runtime analysis to complement the static evidence. Together, those signals help inform removal decisions, without guaranteeing that an API is safe to delete.

Quasar complements [Revapi](https://revapi.org/) for API compatibility analysis and [Kythe](https://kythe.io/) for code navigation by connecting API changes with actual usage across repositories. SCIP supports usage queries across Java, Go, Python, JavaScript/TypeScript, and Rust, while compatibility analysis covers JVM APIs and Protobuf changes traced through generated Java code. Netflix exposes findings through REST, GraphQL, and a [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) server for developers and coding agents.

Netflix plans to move impact analysis earlier into coding workflows, allowing agents to identify public API changes and retrieve consumer information before pull requests are opened. The goal is to help prepare migration changes while keeping API and release decisions with library producers.
