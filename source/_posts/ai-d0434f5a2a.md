## 正文

React 19.3 [shipped on npm](https://react.dev/blog/2026/09/09/react-19-3) on September 9, and alongside stable View Transitions and Fragment Refs it slips in a smaller but widely welcomed addition, a react-dom [browser() API](https://react.dev/reference/react-dom/browser) that lets a component formally opt out of server-side rendering. Aurora Scharff, who shared the docs, [announced](https://x.com/aurorascharff/status/2090428522590359799) that the reference is now live and available in the Canary channel, where you pass the value to `use()` and the component suspends on the server.

The problem it targets is familiar to anyone doing SSR. Components that read `localStorage`, `window`, or the device timezone cannot produce meaningful HTML on the server, and the existing workarounds were awkward. Developers either flipped a mounted flag inside an effect or guarded rendering with `typeof window !== 'undefined'`, a pattern that causes hydration mismatches the moment the server and first client render disagree.

The new API replaces both:

```
import { use } from 'react';
import { browser } from 'react-dom';
function LocalTime() {
 use(browser());
 return <p>{new Intl.DateTimeFormat().resolvedOptions().timeZone}</p>;
}
```

During server rendering, `use(browser())` stops the component and leaves the nearest Suspense boundary's fallback in the HTML. In the browser it returns `undefined`, so the component renders as normal after hydration. It must be called from a Client Component and sit inside a Suspense boundary, or the server render fails. Because `use()` can live behind a condition, a component can defer only when it has to, for example a data hook that renders on the server when a loader supplies `initialData` and opts out otherwise. React also adds an `onBrowserBailout` callback and an optional reason argument so teams can report exactly where server rendering was skipped.

The change first landed as a [React core PR](https://github.com/react/react/pull/37143) that This Week in React [described](https://thisweekinreact.com/newsletter/293) as "eliminating hacky server error-suppression workarounds". In the docs [issue](https://github.com/reactjs/react.dev/issues/8565) tracking the feature, one contributor wrote they were "very excited about the `browser()` api because it solves the client-only component problem in a much cleaner way than the previous ways". Writing about the release, one developer [called](https://abrarqasim.com/blog/react-19-3-view-transitions-stable-the-timeout-hack-i-deleted/) the conditional data-fetching version "the cleanest solution to the 'should this fetch on the server or not' question I've seen".

The approach also narrows the gap with framework-specific escape hatches. Next.js users have long reached for `dynamic(() => import('./C'), { ssr: false })` via [next/dynamic](https://nextjs.org/docs/app/api-reference/functions/dynamic), and Astro exposes a [client:only](https://docs.astro.build/en/reference/directives-reference/) directive, but both are tied to their bundlers. `browser()` moves the capability into React itself, so it works with any SSR setup rather than a single framework.

Upgrading is a standard bump to `react@19.3` and `react-dom@19.3`, following the [React 19 upgrade guide](https://react.dev/blog/2024/04/25/react-19-upgrade-guide), though the [use reference](https://react.dev/reference/react/use) still flags `browser()` as Canary only, so confirm your release channel before depending on it in production.

React is an open-source JavaScript library for building user interfaces, originally created at Facebook and now maintained by Meta together with a large community of contributors. It popularised a component-based model in which the UI is described as a function of state, and it underpins server-side and full-stack frameworks such as Next.js and Remix, as well as native apps through React Native. Since its first release in 2013 it has become one of the most widely used front-end tools, with recent versions leaning further into server rendering, Suspense, and the concurrent features that the `browser()` API builds on.
