## 正文

编译｜林绮蓓

策划｜Tina

微软曾经教全世界的开发者如何写代码，如今，它开始为自己的一部分工程师支付离开的费用。

10 月 26 日，微软宣布推出新的自愿离职方案。11 月 16 日，在《The Pragmatic Engineer》播客中，主持人 Gergely Orosz 向微软 CEO Satya Nadella 提出了一个尖锐的问题：**为什么是现在？这会不会 AI 提效之后，进一步裁员的前奏？**这个问题背后，还有一场让微软始料未及的技术变化。

Claude Code 这个问世才几个月的产品，竟然开始挑战积累了二十多年经验的开发工具。

“我 99% 肯定 Anthropic 公司对微软的任何战略都一无所知，他们也毫不在乎。他们完全无视所有现有技术，开发出了一款非常优秀的工具。”Gergely 感慨。他认为，这件事对微软的冲击将远远超过其他任何事情。“不仅仅是微软，JetBrains 也同样措手不及，同样猝不及防。”

![](/ai-knowledge-qoder/_imgs/47ed4b4e8e49705e.png)

过去二十多年，IDE 几乎一直是软件开发的中心。微软拥有 Visual Studio、VS Code 和 GitHub，还凭借 GitHub Copilot 率先进入 AI 编程市场。即使 Cursor 出现，竞争也仍然发生在微软熟悉的编辑器生态中。这曾是一项看似难以撼动的优势。

Gergely 最近在 X 上回顾微软的 VS Code 战略时，用了三个词概括它：**“拥抱、延伸、熄灭”（Embrace, Extend, Extinguish）**。微软花了十多年时间构建起了一条近乎万无一失的路线：把 VS Code 做得足够出色，开放源代码，让开发者能够自由地在此基础上构建产品，但又很难在开发工具本身的竞争中超越微软。

而 Claude Code 的出现改变了竞争的方式。Nadella 也承认，Anthropic 在模型能力上的重大进展给微软带来了冲击。短短六个月左右，IDE 就在某种程度上“淡出了人们的视野”。

产品上的失速，正在与组织上的重构同时发生。面对自愿离职的问题，Nadella 没有承诺一切照旧。他明确表示，**未来的团队规模、工作流程和人员配置都会不同，微软的 20 万名员工需要以新的方式重新组织。**“我当然希望能够告诉所有人，一切都会和过去一样，但我做不到。”

变化同时也影响着微软对人才的需求。Nadella 透露，对于初级工程师招聘放缓的现象，现在就断言这种趋势会长期持续还为时过早。企业需要先建立新的“软件工厂”，重新安排人员和 Token 资源，才能决定未来需要怎样的工程师。

这场访谈因此有了比“AI 能写多少代码”更尖锐的问题：当代码越来越便宜，微软过去几十年积累的工具优势、组织经验，以及工程师赖以获得回报的能力，还能按原来的方式定价多久？ Nadella 给出的方向是“软件工厂”：人负责规格、意图和验证，Agent 承担越来越多的执行。对于一家靠软件工程建立起庞大帝国的公司，这意味着它必须亲手改造自己的生产方式，也必须重新决定，什么样的工程师值得继续投入，什么样的工作需要被重新安排。

Gergely 在访谈结束后，对微软接下来的变化作出了更直接的判断：“**微软内部还会出现大量组织调整，团队会变小，岗位会变化。自愿离职方案，为那些不愿经历这一轮变化的人提供了退出机会。接下来的变化，很可能会比以往更加密集、更加剧烈。**我想，这种组织重组、岗位变化，以及比过去更强烈的转型压力，也会出现在很多其他科技公司里。”

对于企业在 AI 浪潮中应该守住什么，他的总结同样尖锐：“对一家企业来说，**如果不掌握自己的 AI 基础设施和 AI 知识产权，那实际上是一种自毁式的战略。**Satya 认为，每一家成功的公司都会建立自己的 AI 基础设施，而那些依赖单一供应商或某一家 AI 实验室的公司，正在犯下重大的战略错误。”

## *太长不看版*：

**Gergely Orosz：微软很早就推出了 GitHub Copilot，随后 Cursor 出现，双方不断竞争。但 2025 年 Claude Code 的崛起，让开发者在短短六个月内开始淡化 IDE 的使用。为什么拥有深厚开发者基因的微软，没有第一时间应对这场变化？**

**Satya Nadella：**当模型能力出现非线性跃升时，产品形态就必须迅速改变。这是 AI 优先产品开发非常残酷的地方。你不能迷恋自己已经构建的产品。Cursor 在 Agent 模式上做得很好，随后 Anthropic 的模型进展又让 CLI 成为可行的产品形态，开发者开始把完整任务交给模型处理。不过，我不认为 IDE 会永久消失。随着决策引擎等新能力出现，IDE 甚至可能迎来复兴。

**Gergely Orosz：你多次提到“软件工厂”。如果代码主要由 AI 生成，这种新的软件开发方式究竟意味着什么？**

**Satya Nadella：**在一个代码生成成本已经变得很低的世界里，真正困难的事情变成了验证。代码从输入变成了输出，规格说明、开发意图和验证机制因此变得更加重要。工程师需要把任务交给 Agent，检查任务是否真正完成，并根据失败构建测试用例。还可以利用生产环境日志发现问题、验证修复结果，再将修复部署到生产环境。这仍然是软件工程，只是工程师与代码交互的层次发生了变化。

**Gergely Orosz：微软推出自愿离职方案后，有开发者担心，这是否意味着 AI 提高团队效率之后，公司将进一步裁员。微软为什么做出这个决定？**

**Satya Nadella：**未来仍然会有大量机会，但机会的形态会发生变化，包括团队规模、工作流程和岗位配置。推出自愿离职方案，很大程度上是希望让员工拥有更多自主选择权，根据长期职业发展寻找适合自己的位置。我不能说微软的每个部门都在以同样的速度转型。如果员工觉得自己被困在一个没有跟上变化的团队里，应该能够选择其他机会，包括微软内部的岗位。我希望公司能创造这些机会，但我无法保证一切都会和过去一样。

**Gergely Orosz：很多公司已经放缓甚至停止招聘应届毕业生，因为经验丰富的工程师似乎更能利用 AI 提高生产力。微软怎么看待年轻工程师的招聘？**

**Satya Nadella：**我认为，现在就把招聘放缓视为长期趋势还为时过早。企业首先需要调整内部人员配置和工作方式，建立新的软件工厂，然后才能决定引进什么样的人才。AI 原生公司可能从一名员工和一定的 Token 预算开始，当员工用尽预算后，再增加下一名员工及其 Token 预算。未来更多团队可能采用类似方式，但完成组织重构需要时间，因此应该在更长的时间跨度内观察招聘变化。

**Gergely Orosz：很多公司正在构建自己的 Harness、上下文层和推理基础设施。你认为大多数企业都应该拥有这些系统，并让各个组件可以独立替换吗？**

**Satya Nadella：**完全正确。企业必须掌控自己的学习循环，不能在使用 AI 的过程中泄露最有价值的知识。上下文、记忆、Harness 和模型应该相互分离，否则就可能被某个供应商彻底锁定。我的检验标准很简单：你应该能够替换任何一个模型，同时仍然在自己的私有评估指标上持续改进。如果做不到，就必须问问自己，究竟还能否自主掌控企业的产出。

**Gergely Orosz：企业正在构建大量新的 AI 系统，但很多系统还没有成熟的架构蓝图。你认为企业应该如何应对其中的可靠性和安全问题？**

**Satya Nadella：**我认为企业必须建立信任架构。缩放定律带来了更强的模型能力，但不意味着模型的对齐程度同步提高。我们必须在架构上将智能与权限分离。如果一个不够可靠的 Agent 同时拥有执行权限，就可能带来严重的内部风险。因此，需要把 Agent 当作潜在的内部风险来管理，在运行时建立监控、可观测性、审计日志和安全防护机制，并确保企业始终能够控制自己的学习循环。

**Gergely Orosz：微软正在尝试让闭源模型直接运行在笔记本电脑上。与此同时，你们也在自主研发 MAI 模型。微软未来打算怎样选择和使用这些模型？**

**Satya Nadella：**我们会继续通过合作使用 OpenAI 的模型，同时从零开始构建自己的 MAI 模型家族。我们关注的不只是模型能力，还包括训练阶段的 FLOPs 效率和部署阶段的 Token 效率。未来，一个任务可能由多个子 Agent 完成，不同子 Agent 可以使用不同的模型家族，也可以结合本地与云端模型。我们的目标是让系统根据任务自动选择最合适的模型，而不是始终绑定某一个模型家族。

**Gergely Orosz：如果一名软件工程师希望在未来一两年内，成为 AI 时代非常优秀的工程师，你会给他什么建议？**

**Satya Nadella：**少说一点，多做一点，多学习一些，真正亲自动手体验这些新技术。不要只关注新闻标题或者追逐一轮又一轮的炒作热潮。即使对我自己而言，如果能够改变花在讨论和实际动手上的时间比例，我也愿意这样做。无论你是资深工程师、CEO，还是刚毕业的大学生，都应该尽可能花时间学习和实践，加入真正使用新技术开展工作的团队。我状态最好的时候，往往就是处于学生状态的时候。所以，让我们重新回到学校吧。

## 从开源到 VS Code：微软如何改变软件开发方式

**主持人 Gergely Orosz：**2014 年你出任微软 CEO 时，我其实还在微软工作。我清楚地记得，当时微软仍然非常坚持闭源模式。但你上任之后，微软开始积极拥抱开源。后来，Visual Studio Code 发布了，微软收购了 GitHub，并全面转向 Git，而我们以前使用的是 TFS。TypeScript 也以开源形式发布。

我想回到那个时间点，你当初为什么会做出这样的决定。当时很多人都感到意外，我那些不在微软工作的朋友很惊讶，甚至连我自己也觉得意外。微软为什么决定全面拥抱开源？

**Satya Nadella：**我认为，从某种程度上说，人们对一家公司的认知和评价一旦形成，就很难改变。但如果你回头看看微软过去的工作，就会发现，即使在我出任 CEO 之前，微软也已经向 Linux 提交了大量代码，并且持续投入相关工作。我认为我们当时已经做出了相当重要的贡献。

不过，我觉得我们真正努力做到的一件事，是让微软内部以及外部世界都清楚地认识到：微软坚定地支持开源。无论是将 SQL Server 等微软自身的工作负载引入 Linux，还是直接为 Linux 贡献代码，或者将 TypeScript 等项目开源，这些都是我们参与开源生态的方式。

当然，微软作为 GitHub 的管理者，也让我们处于开源生态的核心位置。我们希望通过真正对社区有益的行动，赢得开源社区的信任。

事实上，这件事很有意思，我一直在思考一个问题：如果我们认真统计一下，各家公司使用了多少开源软件，以及它们各自为开源社区做出了多少贡献，我认为微软很可能排在最前面，即使不是第一，也一定是贡献最多的公司之一。你看其他一些所谓的科技公司，就会发现，其中很多从开源中获益最多的公司，几乎没有做出多少贡献。但人们似乎从来不会这样看待它们。当然，你也没什么好抱怨的，世界就是这样运作的。很多时候，人们相信的是流行的叙事，而不是事实。

**Gergely Orosz：**没错，这确实是叙事与事实之间的差异。我觉得，微软在 20 世纪 90 年代形成的 Windows 时代形象，至今仍然影响着人们对这家公司的看法。不过，在我的印象中，真正对开发者社区产生最大影响的，其实不完全是开源，而是 Visual Studio Code。

VS Code 是开源的，同时也是免费的。我自己也是一名开发者，以前一直使用 Visual Studio，那是一款非常出色的软件。即使是 Visual Studio 2003，放到今天来看，仍然是一款很棒的产品。但微软后来决定，把 Visual Studio 以免费、开源的版本提供给更广泛的开发者社区。结果，五年或者十年之后，VS Code 几乎无处不在，所有人都在使用它。这是你们有意推动的结果吗？

**Satya Nadella：**是的，完全是有意为之。当时，Erich Gamma 和其他参与这个项目的人就是这样考虑的，而且他们从一开始就非常重视与社区共同构建产品。

事实上，当我回顾产品开发的经历时，我发现那也是我第一次真正接触到如今人们经常谈论的“开放式开发”（Building in the Open）。那是我们第一次真正理解，什么叫作以开放的方式构建产品：让社区参与进来，并且围绕社区建立持续的反馈循环。

我记得，当时我还花了不少时间与 Amanda Silver 等人交流，了解那个团队是如何工作的。我尤其想知道，在这样的团队里，产品经理究竟意味着什么，他们每天又是如何利用社区反馈来推动产品开发的。他们的工作方式不再是自上而下地听从管理层的指示，不是“我听副总裁的”，而是“我听社区的”。

所以，我认为，开放式开发带来的改变远远不只是开源本身。它还涉及许多文化层面的变化，而这些变化从根本上改变了我们的产品开发方式。有时候我甚至觉得，我们当时从中学到了很多非常宝贵的经验，但我们本应该把这些经验理解得更加透彻，并将它们推广到更广泛的组织和业务中。

## Claude Code 让微软措手不及，纳德拉认为 IDE 可能复兴

**Gergely Orosz：**说到更深入、更广泛地学习，当时 Visual Studio Code 已经无处不在，GitHub 的发展也非常好。随后，Copilot 出现了。我一直觉得很不可思议，微软竟然那么早就意识到了 AI 在编程领域的潜力。那是在 ChatGPT 和 GPT-3.5 出现之前，我记得当时使用的应该是 GPT-3 的某个版本。Copilot 的表现简直像魔法一样。

至少在接下来的一年里，Copilot 几乎没有真正的竞争对手，直到 2023 年 Cursor 出现。即便如此，我仍然觉得微软在 VS Code 上的布局非常聪明，因为 Cursor 就是基于 VS Code 构建的，开发者对它的界面非常熟悉。GitHub Copilot 和 Cursor 开始并驾齐驱，彼此竞争，也不断追赶对方。

但到了 2025 年，Claude Code 突然出现了。对于我自己，以及那些在初创公司、甚至大型科技公司工作的开发者来说，短短六个月左右，大家似乎就把 IDE 抛在了脑后。这让我至今仍然非常惊讶。微软一直是一家拥有深厚开发者基因的公司，开发者文化可以说早已融入了你们的 DNA。

所以我很好奇，你认为微软为什么没有预见到这场突如其来的转变？这也是我第一次感觉到，面对开发方式的重大变化，微软没有立即拿出应对方案。

**Satya Nadella：**这是一个非常值得深入讨论的问题。正如你所说，我们确实很早就开始探索 AI 编程了。当时甚至还没有 GPT-4，而我们已经开始推进相关工作。即使只是代码补全，那时的效果也已经让人觉得不可思议。如果你还记得，最初的 Copilot 主要就是做这件事。

在此之前，我们已经投入很多年开发 IntelliSense，也取得了不错的进展。但当我们看到 AI 代码补全真正发挥作用时，还是感到非常震撼。坦率地说，当时很多人都怀疑这项技术究竟能不能成功。而当我亲眼看到它开始奏效时，我自己对缩放定律（Scaling Laws）的信心也得到了根本性的强化。

我认为，我们当时在产品开发方面做得不错。但基于模型构建产品，有一个非常关键的特点：当模型能力出现非线性跃升时，产品形态就必须迅速改变。

从这个意义上说，开发一款真正以 AI 为先的产品是非常残酷的。你必须围绕当前模型的能力构建整个产品，同时还要随时做好准备，迎接下一个模型可能涌现的新能力，并据此重新调整产品架构。你不能对自己已经构建的东西过于留恋。

所以，当 Agent 开始具备编程和任务处理能力时，情况就发生了变化。它不再只是补全代码，而是能够接受并完成一些小型任务。Cursor 正是在这个阶段做得非常出色。他们基于 IDE 进行了分叉开发，并且在 Agent 模式上投入了大量精力，取得了很好的效果。

随后，我们也在 Agent 模式上追赶了上来，因为即使基于 OpenAI 的模型，我们同样能够实现这些能力。但接下来真正让我们受到冲击的，是 Anthropic 在模型方面取得的重大进展。他们的模型能力，让命令行界面（CLI）真正成为了一种可行的产品形态。开发者甚至可以直接把完整的编程任务交给模型，让它负责从输入到输出的整个过程。我认为，这才是那六个月里发生的根本性变化。正如你刚才提到的，**IDE 在某种程度上逐渐淡出了人们的视野，取而代之的是一种全新的思考方式：如何将代码及其相关要求作为输入，交给 AI 完成后续工作。**

因此，如果让我重新思考 IDE 的形态，我会更关注如何输入规格说明（Specs）、Markdown 文档，以及围绕“软件工厂”（Software Factory）运行所需的其他信息。整个开发方式都因此发生了变化。

不过，有意思的是，我们现在讨论这个话题时，我又开始产生另一种想法。随着这些决策引擎模型（Decision Engine Models）的出现，我发现自己似乎又重新回到了 IDE。

从某种角度来看，这些模型有点像函数，只不过它们是嵌入软件内部的智能函数。因此，当我们开始思考如何以更高的 Token 效率将智能嵌入软件时，IDE 可能会迎来一次复兴。所以，我并不认为开发方式已经发生了某种永久性的、不可逆转的转变。更准确地说，我们现在需要多种不同的产品形态，让它们分别适应并发挥模型的不同能力。

**Gergely Orosz：**你刚才提到了决策模型，也谈到了自己为什么对这项技术感到兴奋。我们最近都曾在不同场合与 Diego 交流过。我很好奇，你现在对决策模型的看法发生了哪些变化？与此同时，你又如何看待大语言模型（LLM）的局限性，尤其是在程序化任务、编程以及可靠地构建软件这些方面？

**Satya Nadella：**我认为这正是问题的关键。LLM 确实非常出色，但既然我们都是工程师，不妨直接讨论它们表现不够好的地方。比如，当我们思考如何构建软件工厂时，就会遇到很多值得深入讨论的问题。而决策引擎最吸引我的一点，在于它提供了一种新的基础构件（Primitive）。Diego 以及我们自己的决策引擎团队，都在从这个角度讨论这项技术。

这让我想起了 Excel 宏。当年宏给电子表格带来的变化，如今也可能发生在软件开发领域，只不过这一次，我们可以把智能作为一种基础构件嵌入代码之中。举个例子，我最近看到 Xbox 团队构建了一个系统，用来管理社区反馈。这是一个很典型的场景：系统收到社区反馈，然后根据反馈做出一系列决策。在这个过程中，我并不需要让 LLM 不断生成代码，我只是希望系统能够做出决策。因此，更好的办法是把这种决策能力直接嵌入系统，作为一个可以调用的基础构件。这种构件具有自己的概率分布，可以直接调用，不需要每次都重新生成，而且 Token 使用效率更高。我认为，这恰恰说明软件工程依然具有非常重要的价值，只不过它正在发生变化。

我很喜欢 Diego 提出的一个想法：他希望让决策引擎变得像数据库一样平常。事实上，对我来说，关系型数据库一直是非常重要的技术。我刚开始从事软件开发时，除了编译器、Lex、Yacc 等工具之外，最喜欢的开发工具就是数据库。

因为关系型数据库提供了一种可靠的方式来存储和查询信息，让各种各样的应用程序成为可能。我认为，在智能时代，决策引擎也会发挥类似的作用。

**Gergely Orosz：**实际上，数据库才是真正难的部分。我们经常讨论，一家软件公司的核心究竟是什么？答案通常是业务逻辑。但如果深入研究，就会发现，很多业务逻辑实际上存在于数据库之中。过去，大量业务逻辑都是通过存储过程、事务等机制实现的。

**Satya Nadella：**这个类比很有意思。决策引擎或许就是智能时代的存储过程。

**Gergely Orosz：**没错。所以我在想，这是否代表了一种值得期待的发展方向？因为我确实觉得，我们还没有找到正确的基础构件。我们知道 LLM 可以生成代码，也可以用它来处理一些结果不那么可靠的任务，但我们仍然缺少这类能够可靠地嵌入系统的基础构件。

**Satya Nadella：**是的，所以我对这项技术非常期待。

## 代码生成越来越便宜，软件工程师开始构建“软件工厂”

**Satya Nadella：**我认为，这可能是我们重新理解软件开发方式的一个起点。因为还有一个非常重要的挑战。我们不妨回到软件工厂这个话题，看看如今 Claude Cowork 或 GitHub Copilot Runtime 是如何构建的。相关团队已经发表过一些博客文章，其中的内容非常有意思。

**在一个代码生成成本已经变得很低的世界里，真正困难的事情变成了验证。**事实上，我有时候特别希望能加入 Mark Russinovich 和 Scott Hanselman 推动的某个学徒培养项目，不管他们最终怎么称呼这个项目。因为我觉得自己还有很多东西需要学习。我还没有真正加入过这样一种团队：代码主要由 AI 生成，而团队成员的工作重点已经转向管理这些代码产出。

但即使代码已经成为产出，整个工作流程仍然需要遵循特定的操作顺序。这并不意味着每个人都可以随意生成各种代码。你必须先建立相应的验证机制。每当出现一次失败，应该如何根据失败构建测试用例？又该如何确保测试本身确实能够验证问题？

我认为，在管理复杂软件项目的过程中，开发者正在积累大量新的实践经验，其中很多还是没有被正式记录下来的隐性知识。事实上，我记得有一次 Rust 迁移就遇到了非常棘手的问题，团队最终不得不回滚。

所以，这种开发方式既带来了巨大的优势，也存在相当明显的弊端。这也正是为什么我认为，我们需要决策引擎这样的额外基础构件。

**Gergely Orosz：**你刚才提到，自己希望加入这样的团队学习。这让我很感兴趣。作为一家如此庞大的公司的 CEO，你可以看到公司内部正在发生的各种变化，了解各个团队的工作，也能获得大量信息。但如果有机会，你还是希望亲自加入某个团队工作，对吗？

**Satya Nadella：**当然。事实上，如果让我选择下一份理想的工作，我真的很希望重新回到这样的团队。

我甚至想过给 Scott 和 Mark 发封邮件。他们正在微软内部创建一个非常出色的新培养项目，我记得叫作 Preceptorship，似乎还与卡内基梅隆大学有某种合作关系。我非常喜欢这个项目的理念，因为我一直很关心职业生涯早期的工程师如何成长。我们能不能让一名刚进入行业的年轻人加入这样的团队，并帮助他逐渐掌握新的开发方式？我认为，这是一个非常重要的问题。

我记得以前，很多人来微软实习时，会去研究 Dave Cutler 写的代码，或者想办法看看某个重要模块是如何实现的。通过阅读这些优秀工程师编写的代码，他们能够学到很多东西。那么，在今天这种新的开发环境中，与之对应的学习方式是什么？这是我认为我们必须认真探索的问题。所以，我确实希望有一天能够重新获得这样的机会，亲自加入团队学习。

**Gergely Orosz：**现在我开始理解，为什么那么多 CTO、工程副总裁，甚至高级副总裁，愿意放下原来的管理职位，加入规模更小的团队。他们希望亲自学习如何使用这些新工具构建软件，因为眼下几乎所有事情都在发生变化。

**Satya Nadella：**完全正确。我认为，整个组织运作的环境都在发生变化。在这样一个各方面都经历重大转型的时期，更深入地参与实际工作非常重要。不仅是技术本身，与客户保持密切联系、以开放的方式构建产品，这些方面都有大量值得学习的东西。无论是如何打造成功的产品，还是如何开发成功的技术，我们都有很多重新学习和探索的机会。

**Gergely Orosz：**我们已经多次提到“软件工厂”这个词了，不妨现在正式讨论一下。我觉得这个概念目前还有些模糊，但它正在越来越多地被人们提及。对你来说，软件工厂究竟意味着什么？

**Satya Nadella：**其实我自己也仍然在努力理解这个概念。我现在主要通过观察不同团队的工作方式，寻找其中逐渐形成的共同模式，看看今天的软件团队究竟在做什么。

我建议观众去读一下 Bass 写的博客。实际上，有两篇文章很值得看，一篇来自 Cowork 团队，另一篇来自 GitHub Copilot 团队。这两篇文章都展示了很有意思的实践。

GitHub 那边的案例，讲的是一名开发者能够独自维护整个 Runtime。他们似乎还完成了一次语言迁移，我记不太清是不是从 Python 迁移到 Rust 了。反正最后总是要迁移到 Rust。但无论如何，这是一个非常好的案例，展示了单个开发者能够达到怎样的生产力，以及在这种情况下，软件维护工作会发生什么变化。

另一个案例来自 Cowork 团队。我记得整个团队只有 9 名或者 12 名工程师，具体数字我记不清了，但团队规模确实小得惊人。他们围绕软件工厂建立了自己的开发方式，也发表了一篇很好的博客。

这两个案例里有太多让我感兴趣的东西。如果可以，我真希望直接加入那个团队，亲身了解他们是如何工作的，而不只是阅读博客，或者与 Bass 和团队成员交流。

据我的理解，这种开发方式最根本的变化，是代码从输入变成了输出。过去，工程师的主要工作是编写代码，现在代码本身成了系统生成的结果。这意味着，规格说明（Specification）和开发意图（Intent）变得更加重要。当然，过去设计文档也很重要，团队成员之间也需要达成共识，但现在这些事情的重要性进一步提高了。

还有一件事也让我觉得很有意思。我最近和一位职业生涯刚起步的工程师聊过，他告诉我，现在理解一个陌生代码库实际上变得容易多了。原因在于，当你采用软件工厂的方式管理开发工作时，所有事情都会被记录下来，形成文档。这样一来，你就可以直接针对代码库提出问题。

**Gergely Orosz：**就像有了一位非常有耐心的导师，或者一位帮助新人熟悉工作的伙伴。

**Satya Nadella：**没错。这样一来，新人熟悉代码库就容易多了，不必再四处寻找那些只存在于老员工脑子里的隐性知识。

另一个让我学到很多东西的领域是验证。使用 Agent 编程时，你需要把工作拆分成一个个小任务，交给 Agent 执行，然后确保每项任务都真正完成了。但究竟应该如何进行审查和评价？这背后还有很多值得研究的问题。

比如，是否应该使用不同的模型家族来进行评审？这其实是我一直以来非常担心的一件事。如果我们只依赖同一个模型家族，而这个模型家族本身存在某些对齐问题，那么这些问题就可能直接传递到我们构建的软件中。

我们该如何通过独立的评审机制，确保某个模型家族自身的缺陷不会变成我们的问题？这是一个非常重要的挑战。所以，我认为，一种全新的软件开发方式正在形成。这仍然是软件工程，而且仍然需要软件工程师，只不过工程师与代码交互的层次发生了变化。

这也是为什么我很喜欢用编译器的发展来类比。过去，程序员需要自己编写汇编代码。后来有了编译器，大家突然发现，可以直接把自己的意图转换成代码，而不必亲自处理汇编语言。现在的变化与当年有些相似，本质上都是抽象层次的提升。但这一次，改变的不只是编写代码的方式，还包括团队如何协作，以及产品如何被构建出来。

还有一个让我特别兴奋的方向，就是让生产环境中的执行轨迹（Traces）重新反馈到开发过程中。我非常喜欢这个思路。

**Gergely Orosz：**我们一直在讨论可观测性（Observability），但现在可以利用这些数据做更多事情了。

**Satya Nadella：**是的。人们经常谈论递归式自我改进（RSI），而这在某种程度上就是我所理解的 RSI。具体来说，就是利用生产环境中的日志发现问题，然后验证修复结果。这个验证闭环非常重要：你可以根据实际运行情况生成修复方案，完成验证，再将修复部署到生产环境，并确保它真正通过了所有测试。

我认为这非常有价值。如今，微软内部的很多团队都在探索类似的工作方式，并且开始相互学习。这些实践正在逐渐传播到整个微软，也开始改变团队的组织和运作方式。

另一个我非常喜欢的案例来自 Azure 网络团队。事实上，这曾经是我最喜欢讲的一个故事。这个团队告诉我，微软为了运营自己的全球网络，需要与世界各地大约 500 家光纤网络运营商打交道。由于这些都是物理基础设施，难免会时不时出现各种问题。

我们通常会用一个听起来很专业的词来描述这些管理工作，那就是 DevOps。但实际情况往往是，团队需要处理大量电子邮件，以及各种临时建立的工作流程。于是，他们构建了一整套 Agent 系统，让系统直接负责这些运维工作。而且，这套运维系统还与代码仓库连接在一起。这样一来，系统管理的就不再只是代码仓库或者代码库本身，还包括围绕它们展开的实际运维工作。

因此，你可以看到，技术团队的工作性质正在发生变化。过去，团队需要亲自完成各种软件开发和运维任务；现在，他们开始构建由软件和运维流程共同组成的“工厂”，让这些系统代替自己执行任务。当然，工程师仍然在完成工作，只不过他们工作的方式已经有所不同。

## AI 转型不是换个框架：微软正在重构 Windows 和 GitHub

**Gergely Orosz：**我一直在思考一个问题。在 AI 实验室里，软件工程师的工作正在转向帮助 Agent 和整个执行循环更好地运转，这已经是相当普遍的现象，而且这些实验室也很愿意公开分享自己的实践。这与你刚才描述的变化非常一致。

但如果回到实际工作中，情况可能没有那么简单。像微软这样的公司，当然会有一些团队能够尝试新技术，构建新的软件工厂。比如平台团队，他们可能有额外的时间和资源来探索这些事情。但与此同时，你们还有大量产品团队，他们已经有成熟的产品，也有真实的客户。

我发现，很多已经建立起成熟业务的公司都会面临这样的困境。他们看到 AI 实验室展示的各种新型开发方式，或者现在听到你谈论软件工厂，可能会想：等等，我不可能放下手头所有工作，转头去构建一个软件工厂。即使真的建好了，我又该拿它做什么？

所以，你如何看待这两者之间的平衡？尤其是在微软内部，你会怎样向工程师解释他们的工作正在发生什么变化？如果他们负责的是一款已经很成功、能够持续盈利，而且有大量客户依赖的产品，他们应该怎么做？

**Satya Nadella：**这是一个非常好的问题。首先，我们不能因为一项技术看起来很酷，就去做那些不能为客户创造价值的事情。这是最基本的原则。

当然，我们自己也犯过这样的错误。有时候，仅仅因为某种 AI 技术很新颖、很有意思，我们就投入资源去做一些实际上没有明确价值的事情。我想，很多公司都有过类似的经历。

**Gergely Orosz：**所有人都干过这种事。

**Satya Nadella：**没错，所有人都干过，我自己也不例外。我希望自己已经从这些经历中吸取了教训，以后能够做得更好。

不过，我们不妨看看一个非常现实的例子。今天，当我关注 Windows 中的 CVE，也就是公开披露的安全漏洞时，情况已经发生了变化。因为现在有 AI 模型能够主动发现这些漏洞。这意味着，我们现在必须想办法修复所有这些漏洞，因此需要建立一套新的处理流水线。

事实上，如果你看看 Windows 团队正在做的事情，从收集崩溃信息、分析执行轨迹，到最终完成问题修复，他们实际上正在构建一种新型软件工厂。但这里有一个重要区别：这不是一个从零开始的新项目，而是在现有系统上进行改造，也就是所谓的棕地项目（Brownfield Project）。

Windows 原有的构建系统仍然是 Windows 的构建系统。事实上，对于所有这类既有项目来说，最困难的部分往往是构建系统和 CI/CD。

再比如 GitHub。如果你看看它底层正在经历的变化，就会发现情况同样如此。突然之间，大量 Coding Agent 开始在 GitHub 上工作，平台的使用规模急剧增长，甚至达到了过去难以想象的程度。

**Gergely Orosz：**已经是超越人类开发者的规模了。

**Satya Nadella：**没错。因此，我们必须从根本上改变整个系统，包括 Git 协议和底层存储系统。我们正在重新审视并改造其中的每一个部分，确保它们能够适应这种变化。

但我们必须在现有系统的基础上完成这些工作，而不是抛开一切重新开始。当然，我们始终会开展一些从零构建的绿地项目（Greenfield Project），但现实世界中的大部分工作都发生在棕地环境中。

而在棕地项目里，你必须循序渐进地提高系统的可靠性，重新思考各种核心基础构件。从源代码管理，到构建系统，再到 CI/CD，都必须能够在现有项目中正常运转。

这些改变需要时间，需要投入，也需要认真思考。尤其重要的是，整个改造过程必须遵循正确的操作顺序。先做什么、后做什么，会直接影响最终结果。

所以，我希望微软的团队能够理解，这场转型并不是说，我们发现了一项令人兴奋的新技术，于是专门成立一个团队去研究它，而公司的其他人仍然沿用过去的工作方式。

我很喜欢这次转型的一点，就是公司里的每个人都有机会使用新的工具链和工作方式，解决自己面前的实际问题。无论你负责的是 Windows、SQL Server，还是某项云原生服务，都可以使用这些新工具来改进自己的工作。我认为，这正是我们现在看到的变化。

**Gergely Orosz：**不过，公平地说，这听起来与我们过去引入新技术的方式似乎没有太大区别。比如当年 React 作为一种新的前端技术出现时，所有人都想使用它。但没有人会因此获准暂停手头的全部工作，专门把现有项目迁移到 React。相反，当你开发一款新产品，或者为现有产品增加新功能时，就可以逐步引入 React，让新旧技术在同一个项目中共存。

**Satya Nadella：**这是一个很好的问题。有时候，我也会觉得，这种情况以前似乎经历过，并不是什么全新的事情。但我认为，这一次确实有一个非常重要的不同之处，那就是我们完成工作的基本方式正在改变，包括整个操作顺序，以及我们所处的抽象层次。

## 企业不能把一切交给模型：如何掌控 AI 系统与数据

**Gergely Orosz：**现在，我们已经讨论了各家公司如何构建自己的软件工厂，以及如何改变现有的工作方式。接下来，我想进一步聊聊这些变化具体是如何实现的。

最近，我注意到整个科技行业出现了一个非常明显的趋势，相信你也观察到了：越来越多的科技公司开始采用开放模型。很多公司正在自行部署推理基础设施。还有一些公司，比如 Revolut，甚至会直接购买用于推理的硬件，例如 NVIDIA B200，然后在这些硬件上部署模型。

当然，每家公司都有自己的考虑。但从你的角度来看，微软本身也在通过 Foundry 等平台提供开放模型服务。你认为这一趋势究竟有多大？它是否不可避免？我一直在思考，过去的开源软件运动与如今的开放模型运动之间，是否存在某种相似之处？

**萨提亚·纳德拉：**我认为两者之间肯定存在相似之处。未来仍然会有闭源模型，不同闭源模型之间也会继续竞争。与此同时，开放模型会成为闭源模型之外的另一种选择。开放模型能够提供更大的灵活性。

事实上，我思考这个问题时，经常会从另一个角度出发：一个由前沿模型组成的生态系统，究竟应该是什么样子？如果我们不再执着于这样一种想法：未来只会有一个掌握全世界所有知识的前沿模型，那么就必须考虑另一种可能性。从某种意义上说，世界上有多少家公司，就应该有多少个前沿模型。

为什么这么说？我们可以回到经济学家哈耶克对经济体系的解释。他认为，经济运行的一个核心特征，就是知识分散在不同的个体和组织之中。

他关于价格机制的论述非常精彩，解释了为什么价格能够发挥作用。因为知识往往是隐性的，而且分散在整个经济体系中。每家公司都需要掌握并运用自己的知识。

如果接受这一点，那么我甚至会认为，每家公司实际上都同时拥有两种资本：人力资本（Human Capital）和 Token 资本（Token Capital）。

如果未来每家公司都同时拥有这两种资本，那么 Token 资本就可以体现为一个开放权重模型（Open-weight Model），公司可以将自己的知识嵌入这个模型之中。这是一种方式。

当然，企业的知识也可以保存在上下文层（Context Layer）中。你甚至可以同时使用多个闭源模型，收集这些模型在实际使用过程中产生的执行轨迹（Traces），再利用这些数据训练一个属于自己的小模型或者开放权重模型，并将它们组合使用。实际上，如果你看看我们构建的 Copilot，无论是 GitHub Copilot，还是其他 Copilot 产品，它们从设计之初就是多模型系统。
