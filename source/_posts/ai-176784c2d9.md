## 正文

Docker[宣布](https://www.docker.com/blog/docker-sandbox-kit-spec-cncf/)将 Sandbox Kit 规范捐赠给 CNCF，其目标是让“AI 智能体能够访问哪些资源”这件事，变得和智能体本身一样具备可移植性。这份采用 Apache 2.0 许可的规范现已升级至 v3 版本，它将一个智能体、它所使用的工具，以及一份经过类型化声明的、所申请的主机（hosts）、凭证（credentials）和卷（volumes）清单，统一打包为一个普通的 OCI 镜像。

像[Claude Code](https://claude.com/product/claude-code)和[Codex](https://openai.com/codex/)这样的智能体，会代表用户安装包、调用 API 并使用凭据。而那些让它们真正发挥作用的授权，例如，绑定挂载（bind mount）、范围过宽的令牌（broad tokens）、被放开的防火墙规则，通常会散落在 shell 的历史记录、各类控制台看板以及人的记忆之中，而非存放在某个可供审阅的构件（artifact）里。Docker 认为，这正是 OCI 当初被创造出来所要防止的碎片化问题，否则，每一个运行时厂商都可能各自发明一套自己的解决方案。

在[v3](https://www.docker.com/blog/docker-sandbox-kit-spec/)版本中，Kit 不再是一种独立的构件类型。它没有自定义的媒体类型（media type），也没有附属的边车文件（sidecar file）。其清单（manifest）中只包含一项声明：`vnd.docker.sandbox.kit.descriptor`。因此，一个 Kit 可以用`docker buildx build`来构建、用`docker pull`来拉取，并且能够被扫描、签名，或在`FROM`指令中引用。一旦固定（pinning）了摘要（digest），就等于把内容与权限一起固定了下来。

各项声明都是具有类型化、版本化的能力（capabilities），例如，`com.docker.sandbox/network-policy@2`和`com.docker.sandbox/credential@1`。在该规范的 GitHub CLI 示例中，这个 Kit 允许访问`api.github.com`，但拒绝对`/repos/**`执行`DELETE`操作，因为"拒绝"的优先级高于"允许"。凭据可以由代理（proxy）来托管：一个符合规范的运行时会把真实的令牌注入到发往指定域名的请求中，而在沙箱内部只存在一个哨兵值（sentinel value）。

Kit 只是"申请"权限，最终由主机（host）来裁定。如果缺乏符合规范的运行时，这条注解（annotation）就是无效的。倘若某项必需的申请无法满足，启动就会被拒绝。Docker Sandboxes（它在拥有独立内核的 microVM 中运行智能体）是第一个符合规范的运行时。

启动时，会将一个工作负载 Kit（它提供根文件系统）与任意数量的混入叠加层（mixin overlays）组合起来。混入的排序依据的是`provides/requires`的依赖图，而不是命令行标志（flag）的先后顺序。如果某个`requires`未得到满足，或者有两个 Kit 提供了同一个名称，解析就会失败。相互重叠的声明会进行协调（reconcile）：网络规则取并集（unioned），而不兼容的规则则被视为错误。

每一份描述符（descriptor）还可以归约为一组规范化的授权集合。对更新进行门控（gates）的运行时，可以记录这一集合，并阻止任何将其范围扩大的新版本，包括移除了 deny 规则的版本。Docker 表示，随规范一同交付了两套一致性测试套件，一套针对 Kit 构件，一套针对运行时。

Docker 表示，它会与 AWS、Box、Datadog、Dynatrace、JFrog、NanoClaw、OpenClaw、Palo Alto Networks 以及 Snyk 等公司携手打造 Kits。该公司将其与当年捐赠镜像格式和 runc、最终催生出 OCI 的举措相类比。CNCF 的 CTO Chris Aniszczyk 对这一举措表示欢迎：

> 标准是让一个生态能够在不发生碎片化的前提下快速向前的关键，而很少有公司比 Docker 更懂得这一点。通过将 Sandbox Kits 交付为标准的 OCI 镜像，Docker 正在为整个行业提供一种开放的、可重复的方式，把 AI 智能体、它的工具以及它的护栏（guardrails）打包为单一的构件。

不过，这些帖子并未说明该规范是否已被纳入 CNCF 的某个孵化项目，也未提及它将进入哪一个成熟度等级。

希望进行尝试的工程师可以访问`docker/sandbox-kit-spec`仓库，示例可以通过`sbx CLI`进行测试（例如，`sbx run ./hello --kit ./gh`）。虽然现有的镜像仓库、扫描工具和签名工具无需任何改动即可处理 Kits，但描述符语法以及每一项能力的具体语义都是全新的，需要重新学习。需要特别注意的是，权限执行完全取决于运行时。由于 Docker Sandboxes 目前是唯一符合规范的实现，跨不同运行时的可移植性尚未得到验证。在治理结构发生变更之前，Docker 将继续维护该规范，并鼓励社区就任何当前尚无法表达出来的 Kit 职责或运行时职责提供反馈。
